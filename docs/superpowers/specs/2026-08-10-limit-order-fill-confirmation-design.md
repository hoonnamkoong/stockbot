# 매수 지정가 + 체결 확인 원장 — 설계

- 날짜: 2026-08-10
- 대상: 프로그램 매매의 주문 방식과 원장 기록 시점
- 관련 원칙: [[program-trading-parity-mandate]] (심 = 실전 동일 동작, 원장은 fail-closed),
  [[no-fabricated-financial-values]] (추정값을 확정인 척 기록하지 않는다)

## 문제

### 1. 시장가라 체결가를 통제할 수 없다

프로그램 매매는 전량 시장가다(`ORD_DVSN='01'`, `ORD_UNPR='0'`). 심이 판단한
가격과 무관하게 호가에 끌려간다. 사용자 요구는 **"원하는 가격에서만 체결"** 이다.

### 2. 원장이 "주문 = 체결"을 전제한다

`src/pipeline/workers/program_trader.py`의 주문 집행부는 주문 응답이 `success`면
그 자리에서 원장을 갱신한다.

```python
res = place_order_via_vercel(side, code, qty, price)
if res.get('success'):          # KIS rt_cd='0' = 주문 "접수" 성공
    accrue_realized_pnl(...)    # 실현손익 누적
    record_sell / record_buy(...)  # 턴 회계
    _apply_order_to_positions(...) # 포지션 반영
```

`success`는 **접수** 성공이지 체결이 아니다. 시장가에서는 장중 거의 즉시
체결되므로 이 낙관적 반영이 대체로 맞았다. **지정가로 바꾸면 이 전제가
상시로 깨진다.**

미체결 시 실제 피해:

| | 원장 | 실계좌 | 결과 |
|---|---|---|---|
| 미체결 매수 | 보유 있음 | 없음 | `reconcile_positions`가 지우면서 "수동 매도 추정"으로 **거짓 기록** |
| 미체결 매도 | 보유 빠짐 | 남아 있음 | 프로그램이 원장 종목만 팔므로 **영구 고착** + 일어나지 않은 실현손익 누적 |

두 번째가 특히 나쁘다. `realized_pnl`은 `effective_budget`(복리)의 근거라
다음 주문 크기까지 틀어진다.

### 3. 원장 가격이 체결 실측이 아니다

주문가를 그대로 `avg_price`/실현손익에 쓴다. 2026-08-10 대덕전자 실측에서
원장 주문가 107,900 / KIS 실제 체결가 108,000이었다. E10에서 `odno` 캡처까지는
했지만 **원장 정정은 미구현**으로 남아 있었다.

## 방식 결정 (사용자 확정)

| 항목 | 결정 |
|---|---|
| 목적 | 원하는 가격에서만 체결 |
| 매수 | **지정가** (심 판단가) |
| 매도 | **시장가 유지** — 손절·트레일링은 체결 자체가 목적 |
| 미체결 수명 | **매 사이클 취소 후 재판단** |
| 매도 기록 | 다음 사이클에 **체결 실측가로 정정** |
| 턴 회계 | 체결가 정정은 **포함**, 수수료 반영은 **제외**(별건) |
| 과거 누적 realized_pnl | 소급하지 않음 |

## 아키텍처

### 핵심 전환

`주문 = 체결` → `주문 → (다음 사이클) 체결 확인 → 원장 기록`.

부수 효과로 원장이 KIS 체결 실측가로 쓰이므로 **문제 3이 매수·매도 양쪽에서
사라진다.** E10이 여기서 완성된다.

### 새 상태: `pending_orders`

원장(`program_positions.json`, 비공개 레포)에 추가한다.

```json
"pending_orders": {
  "353200": {
    "odno": "0007441100",
    "side": "buy",
    "qty": 3,
    "price": 111000,
    "ordered_at": "2026-08-11T09:20:31",
    "applied": false
  }
}
```

**종목당 1건만 허용한다.** 이 제약이 곧 중복 주문 방지다.

`applied`가 매수/매도의 비대칭을 드러낸다:

| | 주문 직후 | 다음 사이클 |
|---|---|---|
| **매수** (`applied: false`) | 원장 미반영, pending만 등록 | 체결분을 실측가로 **신규 반영** |
| **매도** (`applied: true`) | 추정가로 **즉시 반영** | 실측가로 **차액 정정** |

매도를 즉시 반영하는 이유: 반영하지 않으면 다음 사이클에 같은 종목을 또 판다.

### 사이클 순서

```
1. 원장 락 획득
2. [신규] pending 정산       ← 심 판단보다 반드시 먼저
3. 심 판단
4. 주문 집행
5. 원장 저장 + 락 해제
```

2번이 3번보다 앞서야 한다. 정산 전에 판단하면 심이 낡은 보유 상태를 본다.

### pending 정산 규칙

각 pending에 대해 `find_execution_by_odno`(TTTC8001R, 기존)로 체결을 조회한다.

**매수 (`applied: false`)**

| 조회 결과 | 처리 |
|---|---|
| 전량 체결 | 실측가·실측수량으로 `_apply_order_to_positions`. pending 제거 |
| 부분 체결 | 체결분만 반영, 잔량 취소. pending 제거 |
| 미체결 | 취소만. 원장 불변. pending 제거 |
| 조회 실패 | **pending 유지**, 원장 불변, 다음 사이클 재시도 |
| 취소 실패 | **pending 유지** → 새 주문 안 냄 |

**매도 (`applied: true`)** — 주문 시 추정가로 이미 반영돼 있다.

| 조회 결과 | 처리 |
|---|---|
| 전량 체결 | `realized_pnl += (실측delta − 추정delta)`. `by_tag`도 같은 차액 정정. pending 제거 |
| 부분 체결 | 위 정정 + **안 팔린 수량을 `positions`에 복원**하고 그만큼 되돌림 |
| 미체결 | **전량 복원** (시장가 미체결은 드물지만 거래정지·하한가에서 발생) |
| 조회 실패 | **pending 유지**, 원장 불변, 다음 사이클 재시도 |

부분·미체결 복원이 없으면 "팔았다고 기록했는데 실제로 남아 있는" 고착
포지션이 생긴다.

### 지정가로 무엇을 거는가

**심이 판단한 가격이다. 현재가가 아니다.**

지금 매수 경로는 드리프트 통과 후 판단가를 현재가로 덮어쓴다:

```python
allowed, live_px, why = check_buy_drift(code, price, _price_quote)
if live_px:
    price = int(live_px)   # ← 이 교체가 지정가에 적용되면 안 된다
```

시장가 시절에는 이 값이 기록용이라 신선한 쪽이 나았다. 지정가에서는 이 한 줄이
**기능 전체를 무의미하게 만든다** — 현재가로 지정가를 걸면 사실상 시장가다.

따라서 지정가는 **심 판단가(`candidate`의 가격)** 를 쓰고, `live_px`는 드리프트
판정에만 쓴다. 원장에 남는 체결가는 어차피 다음 사이클의 실측으로 덮인다.

### "다음 사이클"은 60초 뒤다

`scripts/trade_loop.py`가 런 하나에서 두 바퀴 돈다(`TRADE_INTERVAL_SEC = 60`).
태스커 트리거는 2분이지만 정산 주기는 **60초**다. 런이 바뀌면 컨테이너도 바뀌므로
`pending_orders`는 반드시 원장(비공개 레포)에 있어야 하고, 메모리에 두면 런
경계에서 통째로 사라진다.

### 중복 주문 방지

매수 후보 필터가 현재 `code in positions`만 본다.
**`code in pending_orders`를 함께 봐야 한다.**

이 한 줄이 빠지면 2026-07 진흥기업 5연속 매수가 재현된다. 그때 원인도
"원장이 비어 있어 중복 판정을 못 했다"였다.

### `odno`를 못 받은 경우

`_extract_odno`는 `'UNKNOWN'`을 빈 문자열로 돌려준다(추정 매칭 금지).
주문번호가 없으면 그 주문은 추적할 수 없다.

- **매수**: pending 등록 불가 → 경보. 그 주문은 다음 사이클에 미아가 된다
- **매도**: 정정 불가 → 경보. 추정값이 확정인 척 남는다

두 경우 모두 `src/alerts.py`로 사람 경로에 알린다. 추정 매칭으로 때우지
않는다 — 틀린 손익은 없는 손익보다 나쁘다.

## 새로 만들 것

| 항목 | 상태 |
|---|---|
| KIS 주문취소 (`TTTC0803U`) | **신규** — 파이썬 + `/api/trade/order` 계열 라우트 + 테스트 |
| 지정가 주문 (`ORD_DVSN='00'` + `ORD_UNPR`) | `buildOrderRequest`(TS)에 분기 추가 |
| pending 정산 로직 | **신규** — 순수 함수로 분리해 테스트 |
| 체결 조회 | 이미 있음 (`src/trade/executions.py`) |

`buildOrderRequest`는 시장가 규칙(`ORD_UNPR='0'`)을 테스트로 지키고 있다
(683cc55 회귀 방지). 지정가 분기를 넣을 때 **그 테스트를 깨지 않아야** 한다 —
매도는 여전히 시장가이므로 기존 케이스가 그대로 살아 있어야 한다.

## 테스트 전략

순수 함수로 뺄 수 있는 것을 최대한 뺀다. 네트워크에 붙어 있으면 회귀를
테스트로 막을 수 없다(`buildOrderRequest`를 뗀 것과 같은 이유).

- **pending 정산**: 원장 dict + 체결조회 결과(가짜)를 넣고 결과 원장을 검사.
  매수/매도 × 전량/부분/미체결/조회실패 = 최소 8케이스
- **중복 방지**: pending에 있는 종목이 후보에서 걸러지는가
- **매도 차액 정정**: 추정 −3,500 → 실측 −3,723이면 원장이 정확히 −3,723이 되는가
- **복원**: 부분·미체결 매도 후 `positions` 수량과 `realized_pnl`이 원상복구되는가
- **지정가 주문 조립**: 매수는 `ORD_DVSN='00'` + 단가, 매도는 `'01'` + `'0'`

## 성공 기준

배포 후 측정한다. 특히 첫 항목은 **전략이 바뀌었는지**를 가르는 값이다.

1. **체결률** — 매수 주문 대비 체결 건수. 배포 전 대비 급락하면 재검토
2. 원장 `avg_price` vs KIS 체결 실측가 일치 (오차 0원이어야 함)
3. 매도 `realized_pnl` vs KIS `TTTC8715R` 실측 (수수료 오차 ~4원 이내)
4. `pending_orders`가 사이클을 넘겨 쌓이지 않음 (조회·취소 실패 시에만 유지)
5. 중복 주문 0건
6. 고착 포지션(원장에 없는데 실계좌에 남은 것) 0건

## 위험

**체결률 하락으로 전략이 무력화될 수 있다.** 지정가를 걸면 가격이 위로
도망가고, 다음 사이클에 더 높은 판단가로 다시 걸고, 또 도망가는 식이 될 수
있다. 상승장 데이트레이딩(`sim4_bull_daytrading`)에서 특히 그렇다.

하루 8건 사던 것이 2건이 되면 그건 버그가 아니라 **전략이 바뀐 것**이다.
성공 기준 1번이 이걸 잡는다.

롤백은 지정가 분기를 매수에서도 시장가로 되돌리면 된다. pending 구조는
남겨도 무해하다(시장가는 다음 사이클에 전량 체결로 확인된다).

## 범위 밖

- **턴 회계의 수수료 반영** — 2026-08-10 결정대로 제외. 턴은 "체결가는 실측,
  수수료는 미반영" 상태가 된다
- **과거 누적 `realized_pnl` 소급** — 과거 매도 이력이 원장에 없어 불가
- **`check_buy_drift`** — 지정가로 판단가에 걸면 비싸게 살 일이 없어 의미가
  약해지지만, 체결 불가능한 주문을 안 내는 값은 있어 일단 둔다
