# 당일 채택 종목 고정 (Sticky Daily Universe)

**작성일:** 2026-07-10
**상태:** 설계 승인됨, 구현 대기

## 문제

한 번 스크래퍼에 채택된 종목이 같은 날 안에서 리스트에서 사라진다. 원인은 둘이다.

**1. 후보 유니버스가 매 런 새로 뽑힌다.** `analyzer.get_top_trending_stocks()`는 네이버 거래량 상위 페이지를 매번 긁는다. 게시글 조건을 따지기 전에, 거래량 순위에서 밀리면 애초에 조회 대상이 아니다.

예: 흥구석유는 2026-07-10 10:32 런에 69건으로 잡혔고 11:32 런에 99건으로 다시 잡혔으나, 그 사이 11:02 런에는 없다. 게시글은 계속 늘었을 테니 그 시점에도 임계값 80을 넘었을 가능성이 높다. 거래량 상위에서 잠시 밀린 것이다.

**2. 시간대별 임계값이 계단식으로 올라간다.** `PipelineContext._calc_threshold()`는 9시 40, 11시 80, 15시 120을 반환한다. 9시에 45건으로 채택된 종목은 11시에 70건이 되어도 탈락한다.

두 경로 모두 "오늘 뜨거웠던 종목"의 흔적을 지운다. 대시보드는 매 런 전량 덮어쓰기라 화면에서도 사라진다.

## 목표

- 당일 채택된 종목은 거래량 상위에서 빠져도, 임계값을 못 넘겨도, **그날 안에는 계속 추적하고 리스트에 남긴다.**
- 임계값은 **신규 채택 기준**으로만 쓴다.
- 날짜가 바뀌면 초기화한다.

## 비목표

- **매매 동작은 바꾸지 않는다.** 추적 종목은 시뮬레이터·실전 매매의 매수 후보로 넘기지 않는다.
- 추적 종목의 AI 요약을 매 런 갱신하지 않는다 (Gemini 호출량 유지).
- 임계값 계단 자체는 손대지 않는다.

## 설계

### 상태 저장소

`data/daily_adopted.json` — 새 파일.

```json
{
  "date": "20260710",
  "stocks": {
    "002990": {
      "name": "금호건설",
      "market": "KOSPI",
      "adopted_at": "2026-07-10 09:02:10",
      "last_active_at": "2026-07-10 14:32:50",
      "ai": { "posts_summary": "...", "sentiment": "Positive", "keywords": ["..."] }
    }
  }
}
```

`date`가 오늘이 아니면 로드 시 빈 상태로 초기화한다. `data/*.json`은 db-data로 배포되고 런 시작 시 다시 내려받으므로 런 간에 유지된다.

**`sync_state.json`을 확장하지 않는 이유:** `SyncState.stocks`는 종목코드가 키인 dict여야 하는데, 현재 `data_fetcher.py`가 평면 dict(`{'cumulative_count':…, 'last_nid':…}`)를 `.update()`로 병합해 매 종목이 같은 두 키를 덮어쓰고 있다(기존 버그, 후속 참조). 매매 상태 파일에 AI 요약 텍스트를 얹는 것도 관심사 혼합이다.

### Stage 1 — 수집 (`DataFetcherWorker`)

유니버스를 넓힌다.

```
universe = get_top_trending_stocks('KOSPI')
         + get_top_trending_stocks('KOSDAQ')
         + 당일 채택 종목 중 위 목록에 없는 것
```

각 종목의 수급·게시글을 지금처럼 수집한 뒤 상태를 나눈다.

| 조건 | 상태 |
|---|---|
| 게시글 수 >= 임계값 | `활성` |
| 채택 이력 있음 + 임계값 미달 | `추적` |
| 채택 이력 없음 + 임계값 미달 | 버림 (지금과 동일) |

새로 `활성`이 된 종목은 채택 레지스트리에 등록한다.

**거래상위에서 빠진 종목의 시세.** 현재 `current_price`·`change_rate`는 거래량 상위 표에서 온다. `_get_stock_details(code)`가 읽는 네이버 외인 페이지(`frgn.naver`)의 첫 데이터 행에 종가(현재가)와 등락률이 함께 있으므로(`data_rows[0][1]`, `data_rows[0][3]`), 이를 파싱해 채운다. `거래량`·`거래대금`은 그 페이지에 없으므로 0으로 둔다.

**`StockData.status`** 필드를 추가해 `활성`/`추적`을 실어 보낸다. Stage 1은 둘을 합쳐 반환한다.

### Stage 2 — AI 분석 (`LLMAnalyzerWorker`)

- Gemini 배치 분석은 **`활성` 종목만** 대상으로 한다.
- `추적` 종목은 레지스트리에 캐시된 마지막 AI 요약·감정·키워드를 붙인다.
- 분석 후 `활성` 종목의 AI 결과를 레지스트리에 갱신한다.
- 기록(`_persist`)에는 `활성 + 추적` 전체를 넘긴다.

레지스트리 저장은 `_persist` 안에서 한다. 반쪽 런(페이지 실패율 10% 초과)이면 `_persist`가 아무것도 쓰지 않으므로 레지스트리도 갱신되지 않는다. 이는 의도된 동작이다 — 반쪽 런의 낮은 게시글 수로 종목을 새로 채택하거나 AI 캐시를 덮어쓰면 안 된다. 추적 종목은 이미 등록돼 있으므로 다음 정상 런에서 그대로 이어진다.

### Stage 3 — 매매 (`TradeEngineWorker`)

`orchestrator`가 `활성` 종목만 걸러 넘긴다.

```python
active = [s for s in stocks if s.status == '활성']
trade_worker.run(active, sync_state)
```

매매 경로의 동작은 변하지 않는다.

### 기록 형식

`analyzer.save_data()`가 쓰는 세 산출물(고정 CSV/엑셀, 월간 누적 엑셀, 시간별 스냅샷)에 **`상태` 컬럼**을 추가한다.

이게 없으면 백테스트가 추적 종목을 매수 후보로 오인한다. 오늘 청소한 오염과 성격만 다른 새 오염이다.

- 백테스트와 5일/3일 분석기(`analyzer_5days.py`)는 `상태 == '활성'`만 읽도록 필터를 추가한다.
- 대시보드는 둘 다 표시하되 구분한다.
- 기존 행에는 `상태` 컬럼이 없다. 읽는 쪽은 컬럼이 없으면 전부 `활성`으로 간주한다 (2026-07-10 이전 데이터는 전부 활성이었다).

## 데이터 흐름

```
거래상위(네이버)  ─┐
                  ├─> 유니버스 ─> 게시글/수급 수집 ─> 임계값 판정
daily_adopted.json ┘                                    │
                                                        ├─ 활성 ─> Gemini ─> 매매(Stage 3)
                                                        │            │
                                                        └─ 추적 ─────┤ (AI 캐시 재사용)
                                                                     ▼
                                                        기록: 엑셀 3종 + latest_stocks.json
                                                        (상태 컬럼 포함, 반쪽 런이면 생략)
                                                                     │
                                                                     ▼
                                                        daily_adopted.json 갱신
```

## 예상 영향

- 대시보드 행 수가 하루 동안 단조 증가한다. 2026-07-10 기준 09시 4개 → 15시 25개 안팎.
- 월간 누적 엑셀의 런당 행 수가 늘어난다 (대략 2배).
- Gemini 호출량은 거의 그대로다 (활성 종목만 분석).
- 런타임은 유니버스가 커진 만큼 늘어난다. 추적 종목당 페이지 조회가 추가된다.

## 테스트

TDD로 진행한다. 각 항목은 실패하는 테스트를 먼저 쓴다.

1. 채택 레지스트리가 날짜 경계에서 초기화된다
2. 거래상위에 없는 채택 종목이 유니버스에 포함된다
3. 임계값 미달 채택 종목이 `추적` 상태로 리스트에 남는다
4. 채택 이력 없는 임계값 미달 종목은 버려진다
5. `추적` 종목은 Gemini 배치 대상에서 제외되고 캐시된 요약을 쓴다
6. `orchestrator`가 `활성` 종목만 `TradeEngineWorker`에 넘긴다
7. 반쪽 런에서는 레지스트리가 갱신되지 않는다
8. `_get_stock_details`가 현재가·등락률을 파싱한다

## 후속 (이 작업 범위 밖)

- **`sync_state.stocks` 병합 버그.** `data_fetcher.py`가 종목별 상태를 저장하지 않고 평면 dict로 덮어쓴다. 실물 확인됨: `"stocks": {"cumulative_count": 24, "last_nid": "425187924"}`. 종목별 `last_nid`·`consecutive_days` 추적이 사실상 동작하지 않는다.
- **`max_pages = 40` 상한.** 게시글 800건이 넘는 종목(삼성전자 등)은 정확한 수를 알 수 없다.
- **임계값 계단의 의미.** `recent_posts_count`라는 이름과 달리 "직전 런 대비 증가 속도"가 아니라 시각별 누적 하한이다. 이 작업으로 탈락 문제는 완화되지만 이름과 동작의 괴리는 남는다.
