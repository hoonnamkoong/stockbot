# LESSONS_LEARNED.md (교훈 관리)

이 파일은 Antigravity Global Rules 4.5에 따라 개발 및 디버깅 과정에서 식별된 문제의 원인과 해결책을 자산화하여 기록합니다.

## 2026-04-06: KIS 실전 계좌 조회 및 시스템 안정화

### 1. KIS API '에러 7' (조회 이후 자료변경)
- **문제**: 잔고 조회 시 KIS 서버 데이터 갱신 타이밍 불일치로 인해 "조회이후 자료변경" 에러(코드 7)가 빈번히 발생하여 대시보드 조회가 실패함.
- **원인**: KIS API의 일시적 불안정성 또는 데이터 갱신 중 호출 시 발생하는 현상.
- **해결**: 
    - 재시도(Retry) 횟수를 5회로 상향.
    - 재시도 시 지연 시간(Delay)을 단계적으로 늘려(최대 5.5초) 데이터 안착 시간을 확보함.
- **교훈**: 타사 API 연동 시 일시적 오류에 대비한 지연 재시도 로직은 필수임.

### 2. AttributeError (get_portfolio vs fetch_portfolio)
- **문제**: `StrategyAdvisor` 객체에서 `get_portfolio` 속성이 없다는 오류로 인해 텔레그램 리포트 생성 실패.
- **원인**: 코드 개선 과정에서 매서드 이름을 `fetch_portfolio`로 변경했으나, 이를 호출하는 `analyze_candidates` 내부 코드를 수정하지 않은 명명 불일치(Inconsistency).
- **해결**: 호출부의 매서드명을 `fetch_portfolio()`로 수정하여 일치시킴.
- **교훈**: 주요 매서드 이름 변경 시 프로젝트 전체의 참조(Reference)를 반드시 전수 조사해야 함.

### 3. GitHub Token Sync (Direct API Push 실패)
- **문제**: `auth.py`에서 `requests.put`을 사용하여 GitHub에 직접 토큰 파일을 푸시하려 했으나, 텔레그램 전송 전 단계에서 스크립트가 중단되거나 지연됨.
- **원인**: 깃허브 액션 환경에서의 권한 문제나 API 호출의 오버헤드가 메인 스크립트 흐름을 방해함. 이미 `scraper.yml` 시스템에서 자동 푸시를 지원하고 있어 중복된 기능이었음.
- **해결**: 직접 Push 로직을 제거하고, 대신 예외 처리를 강화하여 API 실패가 전체 프로세스(특히 텔레그램)를 멈추지 않도록 절연함.
- **교훈**: 메인 비즈니스 로직(매매/알림) 외의 부가 기능(동기화 등)은 시스템 안정성을 해치지 않도록 철저히 예외 처리하거나 외부 워크플로우에 위임해야 함.

### 4. KIS API (SYDB0050) & 잔고 조회 안정화
- **문제**: 잔고 조회 시 가끔 `SYDB0050` 에러가 발생하여 대시보드 데이터 로딩이 실패함.
- **원인**: KIS API 호출 시 연속 조회용 파라미터(`tr_cont`)가 올바르게 초기화되지 않아 매수/매도 잔고 매칭이 어긋나는 현상.
- **해결**: 모든 KIS API 호출(특히 잔고 및 주문 조회) 전, `tr_cont`를 명시적으로 빈 문자열(`""`)로 초기화하여 첫 페이지부터 조치하도록 강제함.
- **교훈**: 타사 금융 API 연동 시 상태 값이 유지되는 파라미터(Paging)는 명시적 초기화가 필수적임.

### 5. Gemini 429 (Resource Exhausted) & Bulk Sentiment
- **문제**: 수십 개 종목에 대해 개별적으로 Gemini AI를 호출할 경우 API 쿼터(Rate Limit)를 즉시 초과하여 전체 분석이 중단됨.
- **원인**: 루프 내 개별 AI 호출은 비효율적이며 비용(토큰)과 속도 면에서 최악의 선택임.
- **해결**: '2단계 깔때기 분석'을 도입하여 모든 종목의 본문을 하나로 묶어 'Bulk' 형태로 단 1회만 호출하도록 로직을 전면 개편함. 쿼터 방어와 분석 속도 10배 향상 달성.
- **교훈**: AI API 연동 시 '루프 내 개별 호출'은 안티 패턴(Anti-pattern)임. 반드시 묶어서 처리할 것.

### 6. Telegram 누락 방지 (Manual Run Overrides)
- **문제**: `FORCE_RUN`이나 수동 실행 시에도 '분(minute)' 단위 발송 조건에 걸려 텔레그램 리포트가 전송되지 않는 현상 발생.
- **원인**: 알림 보호 로직(`NotificationGuard`)이 스케줄링 실행과 수동 실행을 구분하지 못함.
- **해결**: `is_manual_run` 혹은 `is_forced` 플래그가 활성화된 경우 시간 체크 로직을 완전히 우회(Bypass)하여 즉시 발송을 보장하도록 수정함.
- **교훈**: 자동화 시스템 설계 시 '사용자의 수동 개입(Override)'은 최우선 순위로 보장되어야 함.

### 7. 실거래 수동 주문 방어벽 제거
- **문제**: 대시보드에서 `REAL` 주문을 보낼 때 "시뮬레이션 정책" 에러가 발생하여 실제 주문이 차단됨.
- **원인**: 백엔드 주문 처리 로직(`kis-api.ts`)에 과거 시뮬레이션 모드 운영을 위해 걸어둔 차단 `if`문이 잔존함.
- **해결**: 주문 타입이 `REAL`일 경우 모든 정책 검사를 건너뛰고 즉각 KIS API로 전송하도록 로직을 단순화함.
- **교훈**: 시스템 업그레이드 시 과거의 제약 사항(Legacy Restrictions)이 새로운 기능(Real Trade)을 방해하지 않는지 철저히 전수 조사해야 함.
### 8. 에러 은폐 로직(except: pass)과 데이터 단절
- **문제**: `scraper.py`의 수집부에서 `try...except: pass`를 남용하여 네트워크 오류나 파싱 실패 시 빈 리스트(`[]`)가 반환되어도 시스템이 인지하지 못하고 다음 단계로 넘어감.
- **원인**: 개발 편의를 위해 예외 처리를 생략(Silent Failure)한 결과, 치명적인 데이터 단절이 발생함.
- **해결**: 모든 `except: pass`를 제거하고 명시적인 에러 로깅 및 `raise`를 적용하여 수집 실패 시 즉시 원인을 파악할 수 있도록 함.
- **교훈**: "모르는 게 약"이 아니라 "모르는 게 독"임. 에러는 반드시 시스템 표면으로 드러나야 함.

### 9. 실거래와 시뮬레이션의 완전 망분리
- **문제**: 자동 매매 로직과 대시보드 수동 주문 로직이 혼재되어 자칫 시뮬레이션 중 실계좌 주문이 나갈 위험이 존재함.
- **원인**: 아키텍처 설계 시 '자동=가상', '수동=실계좌'라는 명확한 물리적 분리가 코드 수준에서 강제되지 않음.
- **해결**: `StrategyEngine`에서 KIS API 주문 엔드포인트를 전면 삭제하고, `VirtualPortfolioManager`에 수수료/세금 정산 로직을 내재화하여 순수 논리 시뮬레이션(Logical Paper Trading) 체제로 개편함.
- **교훈**: 금전적 손실이 발생할 수 있는 시스템은 코드 수준에서 '물리적 전원 차단'과 같은 확실한 분리 장치가 필수임.

### 10. AI 출력 포매팅 안정성 (Markdown vs HTML)
- **문제**: Gemini가 리포트 생성 시 HTML 태그(`<b>`, `<i>` 등)를 섞어서 반환할 경우, 텔레그램 API에서 파싱 에러(400 Bad Request)를 일으켜 리포트 전송이 실패함.
- **원인**: AI 모델의 자율성에만 의존하여 출력 형식을 강제하지 못함.
- **해결**: 시스템 프롬프트에 "HTML 금지, 마크다운 강제" 지시를 명문화하고, 반환 직전 정규식으로 모든 HTML 태그를 제거하는 2중 방어막을 구축함.
- **교훈**: 외부 인터페이스(Telegram 등)와 연동되는 AI 출력은 반드시 엄격한 포스트 프로세싱(Post-processing)이 동반되어야 함.

### 11. Gemini 429 (Quota Exceeded) - 모델 스위칭 vs 지연 재시도 (V8.5.6)
- **문제**: `429` 에러 발생 시 즉시 다른 모델(1.5 Flash -> 1.5 Pro 등)로 스위칭할 경우, 모든 모델의 쿼터를 순십간에 소모하거나 호출 폭주로 인해 계정 자체가 차단되는 위험 발생.
- **원인**: 잦은 모델 체인지는 레이트 리밋(Rate Limit)을 해결하기보다 분산된 호출 부하를 가중시키는 안티 패턴이었음.
- **해결**: 모델 스위칭 로직을 폐기하고, 동일 모델에서 **15초간 대기(Sleep)** 후 재시도하는 방식을 채택함. (최대 3회 재시도)
- **교훈**: 쿼터 초과는 모델의 '능력' 문제가 아닌 '시간당 호출량'의 문제임. '회피(Switch)'보다 '인내(Wait)'가 안정적인 해결책임.

### 12. 변수 초기화 누락(UnboundLocalError) & 모듈 경로 관리
- **문제**: 텔레그램 리포트 빌드 중 `msg` 변수 초기화 누락으로 시스템 크래시 발생, 시뮬레이터 임포트 경로 오타로 인한 가동 중단.
- **원인**: 신규 기능(Batch Analysis) 통합 과정에서 로컬 변수의 생존 범위(Scope)를 간과하고, 임포트 파일명과 실제 파일명이 일치하지 않음.
- **해결**: 모든 리포트 빌더 최상단에 명시적 초기화(`msg = ""`)를 강제하고, 시뮬레이터 파일명을 직관적으로 통일함.
- **교훈**: 코드 통합 시 '당연한 변수'는 존재하지 않음. 반드시 초기화 상태를 확인하고, 모듈 경로는 실제 파일 시스템과 1:1 매칭을 전수 검사해야 함.
