# 프로그램 매매 지표 재정의 — 턴 기준 통일 + 주문 단위 대사

- 날짜: 2026-08-14
- 대상: 실전 계좌 화면의 `프로그램 매매` 블록, 프로그램 원장 스키마, KIS 체결 대사
- 관련 원칙: [[no-fabricated-financial-values]], [[program-trading-parity-mandate]],
  [[unknown-vs-zero-in-ui]], [[silent-failure-needs-a-human-path]]

## 문제

화면에 `수익률(누적) +0.88%` / `KIS 실측 실현손익 −13,393원`이 나란히 떠서, 볼 때마다
"왜 다른가"를 사람이 추론해야 한다. 두 숫자는 **범위·대상·기준가가 모두 다르다**:

| | 원장 누적 | KIS 실측 |
|---|---|---|
| 범위 | 프로그램 매매만 | 계좌 전체 |
| 대상 | 실현 + 미실현 | 실현만 |
| 기준가 | 원장 리셋 이후 평단 | 실제 매입가 |

과거에는 수동 매매가 섞여 있어 이 비교가 반쯤 무의미했다. **수동 매매가 없어진 지금은
두 값이 처음으로 같은 범위가 된다** — 즉 이제야 "같아야 하는 값"이고, 어긋나면 원장
버그라는 뜻이다.

또한 원장이 새는 경로가 아직 살아 있는데 그걸 잡을 장치가 없다:

- pending 조회가 UNKNOWN인 채 날짜 경계 스윕에 걸린 주문(2026-08-14 001210)
- `register_pending`이 거부해 정산 대상에서 빠진 매도
- 수수료 요율 근사 오차(2026-08-10 실측 0.12%)

`positions`(현재 보유)와 `realized_pnl`(합계)만 있고 **체결 로그가 없어서**, 원장과 KIS를
주문 단위로 맞춰볼 방법 자체가 없다.

## 결정

1. **프로그램 매매의 모든 지표는 현재 턴 기준이다.** 턴 = 프로그램 스위치 ON~OFF 한 구간.
2. **KIS 실측은 큰 숫자 자리에서 내리고 검증 장치로 쓴다.** 지우지 않는다 — 수동 매매가
   없어져 대조가 유효해진 지금이 오히려 쓸모가 생긴 시점이다.
3. **net = 실제로 낸 비용만 뺀 값.** 보유분은 이미 지불한 매수 수수료만 차감하고, 아직
   발생하지 않은 매도 수수료·거래세는 미리 빼지 않는다.
4. **대조는 주문 단위까지 한다.** 금액 합계만 맞추면 "얼마가 어긋났나"는 알아도 "어느
   주문인가"는 모른다.
5. **지난 턴은 이력 목록으로 남긴다.** 턴 기준을 지키면서 과거 성과도 잃지 않는다.

## ① 화면

숫자는 배치를 보이기 위한 예시다.

```
프로그램 매매                          현재 턴 · 08/12 14:20 ~ 진행 중

수익률              평가손익 (net)        보유 종목 총액      원금
+0.91%             +18,238 원            272,100 원         2,000,000 원
                   수수료 1,204원 차감

전략별 기여도    상승 단타형 (Sim 4-1) +0.91% · +18,238원

┌ ⚠ 원장이 한투 체결과 어긋납니다  ← 불일치일 때만 ──────────────────┐
│ 원장에 없는 체결 1건: 001210 34주 @5,300 (08-12 15:29, odno=0022794600) │
└──────────────────────────────────────────────────────────┘

지난 턴
08/03 10:00 ~ 08/12 14:20 · 원금 2,000,000원 · +12,340원 (+0.62%) · 수수료 2,100원
07/28 09:10 ~ 08/03 10:00 · 원금 2,000,000원 · −4,120원 (−0.21%) · 수수료 1,890원

보유 포트폴리오 (일괄 매도 가능)
[체결금액 · 현재금액 컬럼 — PR #37에서 별도 반영]
```

| 항목 | 정의 |
|---|---|
| 수익률 | `평가손익(net) ÷ turn.capital × 100` |
| 평가손익 (net) | `computeTurnPnl` 결과(턴 확정분 `by_tag` + 보유분 미실현)에서 아래 수수료를 뺀 값 |
| 수수료 | `turn.fees_realized` + Σ `buy_cost(보유 수량, avg_price)` |
| 보유 종목 총액 | Σ `현재가 × 수량` (평가금액) |
| 원금 | `turn.capital` — 분모가 안 보이면 수익률을 검산할 수 없다 |
| 전략별 기여도 | `by_tag` 각 항 ÷ `turn.capital`. **합계 = 수익률** |

**삭제**: `수익률 (누적)`, `평가손익 (누적)`, `KIS 실측 실현손익`, `턴당 수익률`
(마지막은 새 `수익률`과 같은 값이 된다).

**측정 불가 규칙은 그대로 간다.** 원장 조회 실패 → 세 칸 모두 "측정 불가". 시세 결손 →
해당 종목 기여분을 0으로 만들지 않고 표시를 보류한다. 0과 "모른다"를 합치지 않는다.

## ② 데이터 구조

### 수수료 — 소유자를 둘로 쪼갠다

| 값 | 소유자 | 근거 |
|---|---|---|
| `turn.fees_realized` | 파이썬이 원장에 누적 | 매도 체결 시점에만 알 수 있다 |
| 보유분 매수 수수료 | TS가 `buy_cost(qty, avg_price)`로 유도 | 원장에 이미 있는 값 — 필드를 늘리지 않는다 |

이렇게 나누면 **평가손익(net) = gross 합 − 위 둘의 합**으로 정확히 떨어진다.

기록 지점: `_correct_sell` / `apply_confirmed_sell`이 실현손익을 확정할 때 그 매도의
`buy_cost + sell_cost`를 `turn.fees_realized`에 더한다.

### by_tag의 혼재를 푼다

현재 `by_tag`는 **실현분이 net, 미실현분이 gross**로 섞여 있다. 전략별 기여도의 합계가
평가손익(net)과 맞으려면 미실현 쪽에서도 보유분 매수 수수료를 빼야 한다 →
`computeTurnPnl`(TS)에서 처리한다.

### 턴 이력

`config.last_turn_result`(1개 덮어쓰기) → `config.turn_history[]`(배열).

- OFF 시 `freezeTurn` 결과를 배열 앞에 넣고 **최근 20개로 자른다** — config는 GitHub
  파일이라 무한히 키울 수 없다.
- `pnl: null`(측정 불가) 턴도 그대로 남긴다. 실패를 지우면 실패한 적이 없어 보인다.
- 각 항목에 `fees`와 `started_at`을 함께 적는다. 현재 `last_turn_result`에는 `ended_at`만
  있어 "언제부터"를 그릴 수 없다 — `config.turn.started_at`을 동결 시점에 옮겨 담는다.

### 함께 고치는 버그 — `opening_basis` 폐기

같은 턴의 기준가를 두 곳이 다르게 잡는다:

- `route.ts` ON 핸들러 → `opening_basis` = ON 시점 **현재가**(MTM 스냅샷)
- `new_turn`(파이썬) → basis = **매입 평단**. 주석: *"opening_basis는 구 방식의 잔재로
  의도적으로 무시한다"*

그런데 `route.ts`의 폴백 턴(파이썬 첫 실행 전)은 그 무시당하는 `opening_basis`를 쓴다.
**결과: 파이썬 첫 런 전후로 같은 턴의 손익이 점프한다.** 이제 이 숫자가 화면의 유일한
진실이 되므로 **평단 기준으로 통일**한다(파이썬 쪽이 옳다).

### 바꾸지 않는 것

`realized_pnl`(누적)은 그대로 둔다. 화면에서만 빠지고 `effective_budget`(다음 주문 크기)
계산에는 계속 쓰인다.

## ③ 주문 단위 대사

### 체결 로그 — `turn.fills[]`

pending 정산이 **확정될 때만** 적는다(`_enter_position` / `_correct_sell`).
항목: `{odno, code, name, side, qty, price, at, tag}`. 턴 종료 시 이력으로 넘기고 새 턴은
빈 배열로 시작한다.

### 대사 — `reconcile_fills(kis_fills, ledger_fills)`

I/O 없는 순수 함수. `odno`로 매칭해 세 갈래를 낸다:

| 판정 | 뜻 |
|---|---|
| 원장 누락 | KIS엔 체결이 있는데 원장엔 없다 |
| 유령 기록 | 원장엔 있는데 KIS엔 없다 |
| 수량·가격 불일치 | 둘 다 있는데 값이 다르다 |

**함정**: KIS 체결조회는 **누적** 체결수량을 돌려주므로 부분체결이면 같은 `odno`가 여러
줄로 온다. 양쪽 다 **odno별로 합산한 뒤** 비교해야 한다 — 안 그러면 정상 부분체결이
전부 불일치로 뜬다.

### 실행 위치 — 파이썬, 사이클마다

- 이미 2분마다 돌고 KIS 호출도 거기서 한다. 화면이 렌더마다 API를 때리지 않는다.
- **화면을 안 보고 있어도 알아야 하는 문제**다 → `src/alerts.py`로 텔레그램(60분 쿨다운).
- 결과는 `ledger['fill_mismatch'] = {checked_at, items[]}`. 화면 배너는 그리기만 한다.

### 조회 구간

턴 `started_at` **시각 이후**만 본다. 턴이 장중에 시작하면 그날 턴 이전 체결이 섞이므로
날짜만으로는 부족하다 — KIS 응답의 `ord_dt` + `ord_tmd`를 쓴다(`executions.py`가 이미
`time` 필드로 담고 있다).

### 실패 처리

**조회 실패는 "불일치 없음"이 아니다.** `checked_at`이 없거나 오래되면 배너를
**"대조 실패 — 확인 불가"** 로 띄운다. 조용히 초록색이 되면 안전망이 없는 것과 같다.

## 단계

두 단계로 나눈다. ⓐ만 배포해도 화면은 완성된다.

- **ⓐ 턴 기준 재정의**: ① 화면 + ② 데이터(수수료·턴 이력·`opening_basis` 정리)
- **ⓑ 대사기**: ③ 체결 로그 + `reconcile_fills` + 경고 배너 + 텔레그램

## 범위 밖

- 원장 `realized_pnl` 자동 정정(E10 후속) — 이 작업은 **탐지**까지만 한다
- 과거 턴의 소급 재계산 — 이력은 앞으로 쌓이는 것만 담는다
- 심(페이퍼) 화면의 지표 — 프로그램 매매 블록만 건드린다

## 롤백

ⓐ와 ⓑ 모두 표시·기록 계층이라 주문 로직을 건드리지 않는다. 되돌리면 화면이 이전
항목으로 돌아갈 뿐 체결·정산 경로는 그대로다. `turn.fills[]`·`fees_realized`는 읽는 쪽이
없어져도 원장에 남을 뿐 해가 없다.
